# threatdetect: AI threat detection (Ansh's module)

> Student prototype: **model output is a signal for human review, never proof of guilt.**

## What it does

```
examcrypto events.jsonl (signed, hash-chained)
        │  verify hash chain first. If broken: one HIGH "AUDIT_LOG_TAMPERED" alert, then stop
        ▼
behaviour features per actor (10-min / 1-h windows, IST hours; no look-ahead)
        ▼
rules (transparent)  +  Isolation Forest (unusual)  +  Random Forest (learned)
        ▼
risk 0-100 = max(rules, 100·RF, 65·IF)  →  LOW / MEDIUM (≥40) / HIGH (≥70)
        ▼
alerts/alerts.jsonl (AlertStore, review status for the dashboard)
        ▼  HIGH only, optional
Harsh's AuditAnchor.flagRisk (salted pseudonym + score + hashes; no names on-chain)
```

**Design choices (good viva answers):**
- **Isolation Forest alone is capped at 65.** At most it can raise MEDIUM, meaning *review*. It is
  unsupervised and the noisiest of the three detectors, so it never triggers an automatic
  restriction.
- **Why three detectors?** Each covers a different gap. The Random Forest catches learned patterns
  very well but **missed an attack type it never saw (0/6)**. The rules caught it (6/6). See
  `reports/evaluation.md`.
- **Explanations:** each alert lists its reason codes, plus the top features from an exact
  decision-path breakdown of the Random Forest. The test checks that bias + contributions equals
  the model's probability exactly. SHAP was not used, because it isn't needed for this tree model.
- **Alert fatigue:** repeats from the same actor at the same severity within 10 minutes are folded
  into one alert (`suppressed_count`). The count is saved, so it survives a restart.
- **Privacy:** events contain no paper content, keys or tokens (guaranteed by examcrypto's field
  whitelist). On-chain flags use `HMAC-SHA3-256(secret salt, role:actor_id)`, so they cannot be
  reversed by guessing names.
- **Never trusts a tampered log.** The audit log's hash chain is checked before any scoring.

## Data and evaluation: be honest in the report

There is **no real labelled attack data**. The model is trained on **labelled synthetic data**
(normal work by each role plus 6 attack types), generated by `threatdetect/synthetic.py`.
Training uses seed 1 and testing uses an independent seed 2. Metrics in `reports/evaluation.md`:

| Detector (test set) | Precision | Recall | False-positive rate |
|---|---|---|---|
| Rules | 1.00 | 0.85 | 0.000 |
| Isolation Forest | 0.97 | 0.49 | 0.004 |
| Random Forest | 0.99 | 0.99 | 0.004 |
| **Combined** | **0.98** | **0.99** | **0.007** |

These numbers are **optimistic**: the same team wrote both the attack simulator and the rules.
They show that the pipeline works and how the detectors complement each other. They are not
real-world accuracy.

## Commands (Windows PowerShell, from the `ansh` folder, venv active)

```powershell
python -m pip install -r requirements.txt
python -m unittest discover -s tests            # 25 tests
python -m threatdetect train                    # -> models\ (git-ignored; pickle, never load others' files)
python -m threatdetect evaluate                 # -> reports\evaluation.md
python -m threatdetect demo                     # synthetic stream -> alerts
python -m threatdetect score ..\aditya\local_storage\events\events.jsonl
python -m threatdetect watch ..\aditya\local_storage\events\events.jsonl            # live
python -m threatdetect watch ..\aditya\local_storage\events\events.jsonl --flag-on-chain   # + Harsh's chain
```

## Alert format (v1)

```json
{"alert_id":"…","event_time_utc":"2026-11-02T06:10:00Z","event_seq":42,"event_hash":"…",
 "event_type":"RELEASE_REQUEST","paper_id":"pap_…","actor_id":"dev-release_officer","actor_role":"release_officer",
 "risk_score":85,"severity":"HIGH","reason_codes":["INTEGRITY_FAILURE","REPEATED_DENIALS"],
 "top_features":[{"feature":"integrity_fail_1h","value":2.0,"contribution":0.41}],
 "components":{"rules":85,"random_forest":0.97,"isolation_forest":0.12},
 "recommended_action":"TEMPORARY_RESTRICT","status":"NEW","suppressed_count":2,
 "model_name":"threatdetect-rules+iforest+rf","model_version":"0.1.0"}
```

`recommended_action` is `ALLOW`, `REVIEW` or `TEMPORARY_RESTRICT`. The last one needs **human
confirmation** in the dashboard (Nayan's module). The AI never blocks anyone by itself.

## Tests (25, stdlib unittest)

- Synthetic data, features (no look-ahead, windows, IST hours), and every rule.
- Model: the exact explanation property, save/load, and the feature-list guard.
- Scoring: Isolation Forest cap, RF can raise HIGH, every alert has a reason, suppression is persisted.
- Alert store: review history; reviewers cannot edit scores.
- Chain flags: salted pseudonym, payload format, gateway call and gateway outage.
- Cross-module: tests run on **real examcrypto signed events**, check the hash chain is compatible,
  that HIGH alerts are flagged and MEDIUM ones are not, that restarts are safe, and that a tampered
  log produces exactly one system alert and then scoring stops.
- Evaluation report shape and honesty disclaimer.

Mutation-checked: 7 deliberate bugs (Isolation Forest uncapped, suppression not saved, tampered
log trusted, unsalted pseudonyms, windows never expiring, reviewers editing scores, MEDIUM alerts
on-chain) are each caught by at least one test.
