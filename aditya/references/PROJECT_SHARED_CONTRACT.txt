PROPOSED OPTION A
ML-KEM-768 + HKDF-SHA-256 + AES-256-GCM + SHA3-256 + ML-DSA-65, private S3 storage, IAM, cloud monitoring and blockchain anchoring. This updates the crypto design from the existing PPT and is pending approval.

ALGORITHM PURPOSES
- ML-KEM-768: encapsulate/decapsulate shared secret; not file encryption and not signing.
- HKDF-SHA-256: derive key material from the KEM shared secret, with per-paper salt and context separation.
- AES-256-GCM: encrypt/authenticate file bytes. Use a fresh nonce for each encryption key and exact AAD on decrypt.
- SHA3-256: file/manifest digest; define exact bytes hashed.
- ML-DSA-65: signature over a deterministic canonical manifest; verify with a trusted public key.
- S3 SSE-KMS (if configured) is a separate at-rest cloud layer; it does not replace the application's ML-KEM/AES/manifest workflow.

PROPOSED DATA FLOW
1. Validate authorized upload and exam metadata.
2. ML-KEM-768 encapsulation to the approved recipient/release service public key.
3. HKDF-SHA-256 derivation of a per-paper AES key from the KEM shared secret.
4. AES-256-GCM encryption of the PDF with fresh nonce and canonical AAD.
5. SHA3-256 digest of ciphertext; canonical manifest includes identifiers, release time, version, key IDs and crypto parameters.
6. ML-DSA-65 signing of canonical manifest excluding its own signature field.
7. Upload ciphertext + manifest + signature to private S3; emit a sanitized audit event and request a blockchain anchor.
8. Before release, enforce identity/role and time; verify manifest signature and ciphertext digest; decapsulate, derive key, authenticate/decrypt; fail closed on any error.

HASH COMPATIBILITY WARNING
SHA3-256 is not Ethereum keccak256. If a smart contract uses keccak256 for its own calculations, document that separately. Agree on the exact bytes32 digest passed between services and contract.

KEY MANAGEMENT
- Separate recipient ML-KEM key pair from ML-DSA signer key pair.
- Public key distribution and trust anchors must be defined.
- Never store private keys in Git, browser bundles, S3 plaintext objects or blockchain.
- Validate exact KMS algorithm/API/region support before planning KMS-managed post-quantum keys. Do not confuse ML-KEM in a TLS connection with application-level KEM encapsulation.
- Document local-demo key storage as a prototype limitation; plan appropriate managed/hardware-backed protection for real deployment.
